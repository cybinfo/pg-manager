Business Hierarchy Architecture

📅 2026-05-31 ✍ Rajat Seth 📁 ManageKar Platform 🔖 v1.0 Draft

1Why This Document Exists

ManageKar currently has two operational modules — PG Manager and Library Manager. Each module was built with its own "root business entity":

  • PG Manager created properties (buildings with rooms and beds)
  • Library Manager created libraries (library locations with sections and seats)

As we add Gym, Hospital, Hotel, Food, School, and other modules, each will follow the same pattern: create their own root entity with their own name, address, phone, workspace_id, and owner_id columns.

The core problem This is the same fragmentation that existed with identity data before the people table. The people table solved identity for persons. This document proposes solving it for businesses and their physical locations.

2The Problem in Concrete Terms

2.1 — Data Duplication

Today, address and contact data is duplicated per module:

properties.address  = "123 FC Road, Pune"
properties.phone    = "9876543210"

libraries.address   = "123 FC Road, Pune"   ← same building, copied
libraries.phone     = "9876543210"           ← same number, copied

One update to the address requires touching every module table separately. With 6+ future modules, this is unmanageable.

2.2 — No GST / Legal Identity Layer

GST number, PAN, legal business name, and registration number have no home today. They logically belong to a legal entity, not to a PG property or a library. There is currently nowhere to store this data on the platform.

2.3 — No Unified Business View

An owner who runs 3 PGs, 1 library, and 1 tiffin service has no single dashboard view of "my businesses." They see a PG list and a library list — siloed module views with no parent concept unifying them.

2.4 — The Module Explosion Problem

Every new module added to ManageKar currently requires a new root entity table with duplicate address columns, duplicate contact columns, and no connection to existing entities at the same physical address. This is unsustainable at scale.

Gupta Ji: PG at Viman Nagar, Library at Kalyani Nagar, Gym at Aundh.

Developer has "Green Valley Hospitality" (GST₁) and "StudyZone Education" (GST₂) under one ManageKar account.
workspace

  │    └─ location → PG
  └─ business "StudyZone" (GST₂)

workspace
  └─ business "PG One"

       ├─ location "Mumbai"    → PG
       └─ location "Bangalore" → PG
Scenario C is the critical case. Any design that puts address on the operation entity (property/library) breaks immediately when a single building hosts two different module types. This was the flaw in the first design attempt. The Location layer exists precisely to solve this.

4The Three Layers

After mapping all scenarios, exactly three distinct conceptual layers exist between workspace and operational module data. My first design attempt collapsed all three into two — that was the core mistake.

Layer 1
Business

The legal or brand entity. Has a name, GST number, PAN, legal registration. Completely operation-type agnostic — a business can run PGs and libraries and gyms. Owns the GST number.

Layer 2
Location

A physical premises at a specific address. One Business can have many Locations (branches). One Location can host many operation types simultaneously. Canonical home for address data.

Layer 3
Operation

The actual module entities: PG Property, Library, Gym, Hotel, Food Service, etc. Contains the module's internal hierarchy (rooms/beds, sections/seats). One Location can have multiple Operations of different types.

7Proposed Schema

7.1 — businesses table

CREATE TABLE businesses (
  id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  workspace_id        UUID NOT NULL REFERENCES workspaces(id),
  owner_id            UUID NOT NULL REFERENCES auth.users(id),

  -- Identity
  name                TEXT NOT NULL,              -- display / brand name
  legal_name          TEXT,                       -- registered company name
  slug                TEXT UNIQUE,                -- for public URLs /b/[slug]
  description         TEXT,
  logo_url            TEXT,
  cover_url           TEXT,

  -- Legal / Tax (India-first)
  gst_number          TEXT,
  pan_number          TEXT,
  registration_number TEXT,
  business_type       TEXT,    -- proprietorship | partnership | pvt_ltd | llp

  -- Contact
  phone               TEXT,
  email               TEXT,
  website             TEXT,

  -- Meta
  is_active           BOOLEAN NOT NULL DEFAULT true,
  tags                TEXT[] DEFAULT '{}',

  -- Audit
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  created_by          UUID REFERENCES auth.users(id),
  deleted_at          TIMESTAMPTZ,
  deleted_by          UUID REFERENCES auth.users(id)
);

7.2 — locations table

CREATE TABLE locations (
  id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  business_id         UUID NOT NULL REFERENCES businesses(id),
  workspace_id        UUID NOT NULL REFERENCES workspaces(id),
  owner_id            UUID NOT NULL REFERENCES auth.users(id),

  -- Identity
  name                TEXT NOT NULL,              -- "Main Branch", "Koregaon Park"
  description         TEXT,

  -- Address
  address             TEXT,
  city                TEXT,
  state               TEXT,
  pincode             TEXT,
  country             TEXT NOT NULL DEFAULT 'India',
  latitude            DECIMAL(10, 8),
  longitude           DECIMAL(11, 8),

  -- Contact (can override business-level)
  phone               TEXT,
  email               TEXT,

  -- Operations
  opening_time        TIME,
  closing_time        TIME,
  operating_days      TEXT[],   -- ['mon','tue','wed','thu','fri','sat']

  -- Meta
  is_active           BOOLEAN NOT NULL DEFAULT true,
  is_primary          BOOLEAN NOT NULL DEFAULT false, -- marks head office

  -- Audit
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  created_by          UUID REFERENCES auth.users(id),
  deleted_at          TIMESTAMPTZ,
  deleted_by          UUID REFERENCES auth.users(id)
);

7.3 — Changes to existing module tables

-- PG Module
ALTER TABLE properties
  ADD COLUMN location_id UUID REFERENCES locations(id);  -- nullable for migration

-- Library Module
ALTER TABLE libraries
  ADD COLUMN location_id UUID REFERENCES locations(id);  -- nullable for migration

-- Future modules follow the same pattern automatically:
-- gyms.location_id, hotels.location_id, food_services.location_id, etc.
Migration strategy location_id is nullable initially to allow a non-breaking migration of existing data. The goal is to make it NOT NULL after all existing property and library records are linked to a Location via the migration script.

8Naming Decisions and Rationale

Why businesses and not something else

CandidateProblem
organizationsToo corporate — alienates sole proprietors and street-level operators
brandsMisses the legal entity angle — no GST, no PAN, no registration
companiesToo formal — most users are proprietors, not company directors
venturesVague, no clear meaning to a PG/library owner
establishmentsCorrect (GST uses this term) but unfamiliar outside accountants
businesses ✓"Mera business" is natural Indian SMB language. Maps to GST concept. Unambiguous.

Why locations and not something else

CandidateProblem
premisesCorrect (GST "place of business") but formal and unfamiliar
branchesImplies a headquarters hierarchy that may not exist for simple owners
outletsRetail connotation — wrong mental model for PG/library owners
sitesConstruction / technical connotation
unitsAbstract, no spatial meaning
propertiesCONFLICT — this name is taken in the PG module for a different concept
locations ✓Clear, universal, no connotation baggage. Universally understood.
The properties naming conflict The current properties table means "a PG building." If we introduce locations as the physical address layer, the word "property" (which in English also means a physical place) creates conceptual confusion in code. Recommended resolution: keep properties as the PG-specific operation entity name for now. It is an internal table name visible only in code. A rename migration can be considered in a future phase once the hierarchy is stable.

9The Hard Architectural Decisions

These require explicit product/business decisions before any implementation begins. They cannot be resolved purely architecturally.

1
Is Location mandatory, or auto-created silently?
Option A — Mandatory from day one

Every property and library must have a location_id. New records cannot be created without it. Forces the hierarchy from the start.

✓ Clean data model, no nullable FKs, no legacy debt
✗ Creates friction for simple users who just want to add a PG quickly
Option B — Auto-created silently Recommended

When a user creates a PG property without going through Business → Location flow, the system auto-creates both records with sensible defaults (business name = property name, location address = property address).

✓ Zero friction for simple users. Hierarchy exists in data even if user never saw it.
✗ Auto-created Business records will have incomplete data (no GST, no logo). Creates enrichment debt.
Option C — Optional for existing, mandatory for new signups

Existing workspaces are migrated via script. All new workspaces must create a Business before anything else, enforced in the onboarding wizard.

✓ Clean going forward. Migration handles the past.
✗ Two classes of users until migration is complete.
2
What data moves from properties / libraries to locations?

These columns exist on both tables today and become redundant once location_id is populated:

ColumnMove to locations?Notes
address✓ YesCanonical address lives on Location
city✓ Yes
state✓ Yes
pincode✓ Yes
phonePartialKeep on operation too — a library branch may have its own number
name✗ NoOperation keeps its own display name
owner_id✗ NoKeep on operations for RLS
workspace_id✗ NoKeep on operations for RLS

Strategy: Do not delete columns from properties/libraries immediately. Add location_id FK first, populate via migration, then deprecate the old address columns in a later migration once all code is updated.

3
Does workspace change?

No. Workspace stays exactly as it is. It is the auth and billing boundary — one owner account, one workspace, one subscription tier.

businesses sits inside a workspace. They are fundamentally different concepts:

workspace = "your ManageKar account"

business = "a business you run on ManageKar"

A workspace can contain multiple businesses. This is a parallel concept, not a replacement.

4
Module-specific config — workspace, business, or location level?

Currently all config (billing settings, feature flags, notification preferences) lives at the workspace level. With businesses and locations, the question arises: should config be configurable per-Business or per-Location?

Decision for v1: All config stays at workspace level. No change.

Future consideration: Per-business config for billing cycle, currency, GST settings. Per-location config for operating hours, notification recipients. This is explicitly deferred to avoid scope creep in v1.

5
Public URLs — keep /pg/[slug] or move to /b/[slug]?

Today the PG public website is at /pg/[slug]. The slug belongs to a property. With the new hierarchy, the slug logically belongs to a Business (the brand) or a Location (the branch).

URL patternWhat it shows
/b/[business-slug]Business profile with all locations and operations
/b/[business-slug]/[location-slug]Specific branch/location
Keep /pg/[slug] unchangedNo change, fully backwards compatible

Recommendation for v1: Keep /pg/[slug] unchanged. Add /b/[slug] as a new business profile page in a future phase. Both can coexist.

10Migration Plan (High Level)

For existing workspaces that already have properties and libraries:

-- Step 1: For each workspace with existing properties/libraries
-- → Create 1 Business record
--   name = owner display name (or first property name as fallback)
--   gst_number = NULL (owner fills in later via UI)

-- Step 2: For each existing property
-- → Create 1 Location record
--   Copy address, city, state, pincode, phone FROM property TO location
--   Set location.business_id = the business created in Step 1
--   Set property.location_id = this new location's id

-- Step 3: For each existing library
-- → Create 1 Location record (or link to existing if same address)
--   Copy address FROM library TO location
--   Set library.location_id = this new location's id
Production data — use service role This migration runs against production data. It must use the Supabase service role key to bypass RLS — same approach used in the Google Sheets → Supabase library data migration. Script lives in scripts/ and is run once.
Post-migration enrichment After migration, owners are prompted (not forced) to complete their Business profile: add GST number, logo, legal name. This is optional enrichment surfaced in the UI, not a blocker.

13Open Questions — Require Owner Decision

These cannot be resolved architecturally. They require product decisions before implementation begins.

1
Is Location mandatory or auto-created silently when a property is created?
Options: Mandatory from day 1 / Auto-create silently / Optional with enrichment prompt
⚡ Impacts: Onboarding UX, migration complexity, data completeness
2
Does the new-user onboarding start with "Create a Business" or "Create a PG / Library"?
Business-first (hierarchy visible from day 1) vs Module-first (familiar, hierarchy added later)
⚡ Impacts: First-run experience, mental model, perceived complexity
3
Keep /pg/[slug] as-is or migrate public pages to /b/[slug]?
Keep both / Redirect old to new / Replace entirely
⚡ Impacts: SEO for existing public pages, business profile visibility
4
Can a Location have zero active operations (be a "placeholder")?
Yes, valid to pre-create locations / No, must have at least one operation
⚡ Impacts: Data integrity rules, migration edge cases
5
Is Food a v1 module type or deferred to v2?
Build Food as a first-class operation alongside PG + Library / Defer Food to after hierarchy is stable
⚡ Impacts: v1 scope, timeline, schema completeness
6
Are Businesses visible to staff members, or owner-only?
Owner-only (staff only see their module) / All staff (staff see the business they're assigned to)
⚡ Impacts: Permission model, staff UX, RLS policies
7
Should properties eventually be renamed to avoid conflict with the "location" concept?
Yes, rename to pg_properties in a future migration / No, keep as-is (internal name only)
⚡ Impacts: Code clarity, query readability, migration cost

15Analogy Summary

The clearest way to explain why this architecture is correct is through its parallel to the people table decision:

Concept
People Module
Business Module
The problem
Name/phone duplicated across tenants, staff, members
Address/legal data duplicated across properties, libraries, gyms
The solution
people as identity source of truth
businesses + locations as business identity source of truth
The relationship
tenants.person_id, staff.person_id
properties.location_id, libraries.location_id
The 360° view
People detail page: one person across all their roles
Business detail page: one business across all its operations
Principles served
Centralization + Unification
Centralization + Unification + Modularization
The core insight Just as people answers "who is this person regardless of which module they appear in" — businesses + locations answers "what is this business and where does it operate, regardless of which modules are running there."
